
# リファクタリングルール — リーダブルコード基準

> 出典: *The Art of Readable Code* (Boswell & Foucher, 2011, O'Reilly)  
> 本ドキュメントは同書の章構成に準拠し、実装判断に使えるよう再構成したものです。

---

## 基本原則

> **コードは他人が最短時間で理解できるように書く**（第1章）

「動くコード」と「読めるコード」は別物。  
理解コストの最小化を常に第一基準とする。

---

## 1. 命名

### 1-1. 明確な単語を選ぶ（第2章）

| ❌ 避ける | ✅ 使う | 理由 |
|---|---|---|
| `get` | `fetch`, `download`, `compute` | 取得元・処理を明示 |
| `size` | `height`, `numNodes`, `memoryBytes` | 何のサイズかを明示 |
| `data`, `info` | ドメイン固有名詞 | 意味を持たない汎称を排除 |
| `Manager`, `Helper` | 役割を表す名詞 | 曖昧な接尾辞を排除 |

### 1-2. 汎用名を避ける（第2章）

```
// ❌
for (let i = 0; i < results.length; i++) { ... }

// ✅ — ループ変数にも意味を持たせる
for (let userIndex = 0; userIndex < users.length; userIndex++) { ... }
```

ただし、スコープが2行以内の自明なループでは `i` は許容される。

### 1-3. 具体的な名前を使う（第3章）

- `--run-locally` より `--use-local-database`
- `DISALLOW_EVIL_CONSTRUCTORS` より `DISALLOW_COPY_AND_ASSIGN`
- `tmp`, `retval` は「中間値」を表すだけで何も説明しない → 用途を名前にする

### 1-4. 追加情報を名前に付与する（第3章）

| 種別 | 例 |
|---|---|
| 単位 | `delayMs`, `sizeBytes`, `angleDeg` |
| 変換済みフラグ | `rawInput` vs `encodedInput` |
| null 許容 | `userOrNull`, `maybeUser` |
| 処理状態 | `unescapedComment`, `escapedComment` |

### 1-5. スコープに応じた名前の長さ（第3章）

- **狭いスコープ（数行）**: 短い名前で可
- **広いスコープ（モジュール全体・クラス）**: 長く具体的な名前を使う
- 不要な単語は削る: `convertToString()` より `toString()` で十分な文脈では短い方が良い

## 2. コメント

### 2-1. 書くべきでないコメント（第5章）

```
// ❌ コードの繰り返しに過ぎない
// account の profit に tax_rate を掛ける
account.profit *= tax_rate;

// ❌ 名前が悪い → コメントで補うのではなく名前を直す
// 2回目の読み込み試行
retry();
```

### 2-2. 書くべきコメント（第5章）

```
// ✅ なぜその値なのかを説明
// ブラウザの最小タイムアウト実装が約 25ms のため、余裕を持って 30ms に設定
const POLLING_INTERVAL_MS = 30;

// ✅ 将来の読者への警告
// ⚠️ この順序を変えると XSS が発生する（Issue #1234 参照）
sanitize(input);
escape(input);

// ✅ TODO / FIXME ラベル
// TODO: 認証実装後にこの一時的なバイパスを削除する
// FIXME: データが空のとき null を返すことがある
// HACK: ライブラリのバグ回避 (v3.2.0 で修正予定)
```

### 2-3. コメントの精度（第6章）

- 代名詞を避ける: 「それ」「これ」は何を指すか明記する
- 「何をする」より「なぜそうする」を書く
- 入出力例を使う: 関数の動作は例示が最も伝わりやすい

```
// ✅ 例示コメント
// Strip("abba/a/ba", "ab") → "/a/"
function Strip(str: string, chars: string): string { ... }
```

## 3. 制御フロー

### 3-1. 条件式の順序（第7章）

```
// ✅ 変化する値を左、安定した値（期待値）を右に置く
if (length > 10) { ... }       // length が変化、10 が固定
if (received < expected) { ... }  // 直感的な語順

// ❌ ヨーダ記法（特に理由がなければ避ける）
if (10 < length) { ... }
```

### 3-2. if-else の順序（第7章）

1. 肯定・単純・一般ケースを先に
2. 「より目立つ」ケースを先に
3. 早期リターンでネストを減らす

```
// ❌ ネストが深い
function process(user) {
  if (user !== null) {
    if (user.isActive) {
      // 実際の処理
    }
  }
}

// ✅ ガード節で早期リターン
function process(user) {
  if (user === null) return;
  if (!user.isActive) return;
  // 実際の処理
}
```

### 3-3. 三項演算子の節度ある使用（第7章）

```
// ✅ 1行で完結する単純な置換
const label = isError ? "エラー" : "正常";

// ❌ 複雑な分岐に三項演算子を使わない
const result = a ? (b ? c : d) : (e ? f : g); // → if-else に書き直す
```

### 3-4. do-while は避ける（第7章）

- 条件が末尾にあるため、コードを2回読む必要がある
- 同等の while または for に書き換えられる場合は書き換える

### 3-5. ネストを減らす（第8章）

深いネストは「条件スタック」を意識させ理解コストを上げる。

```
// ❌
if (userIsLoggedIn) {
  if (hasPermission) {
    if (dataExists) {
      render(data);
    }
  }
}

// ✅ 早期リターンで平坦化
if (!userIsLoggedIn) return;
if (!hasPermission) return;
if (!dataExists) return;
render(data);
```

## 4. 変数・式の分解

### 4-1. 説明変数を使う（第9章）

```
// ❌
if (line.split(":")[0].trim() === "root") { ... }

// ✅
const username = line.split(":")[0].trim();
if (username === "root") { ... }
```

### 4-2. 要約変数を使う（第9章）

```
// ❌ 同じ条件式を複数回書く
if (request.user.id === document.owner_id) { ... }
// ...
if (request.user.id !== document.owner_id) { ... }

// ✅ 意味を変数に持たせる
const userOwnsDocument = request.user.id === document.owner_id;
if (userOwnsDocument) { ... }
if (!userOwnsDocument) { ... }
```

### 4-3. ドモルガンの法則を活用する（第9章）

```
// 等価変換で読みやすい方を選ぶ
!(a || b) === (!a && !b)
!(a && b) === (!a || !b)
```

### 4-4. 変数のスコープを小さくする（第10章）

- 変数は使う直前に宣言する
- 「一度だけ書き込む変数」を優先する（`const` / `final` / `let` の選択）
- グローバル変数はバグの温床 → 可能な限りローカルスコープに閉じる

### 4-5. 中間変数を削除する（第10章）

```
// ❌ 不要な中間変数
const result = calculate();
return result;

// ✅
return calculate();
```

ただし、**中間変数が意味を持つ場合（説明変数）は削除しない**。

## 5. 関数設計

### 5-1. 関数は一つのことをする（第11章）

「タスクを小さくする」ことが本質。  
関数が複数のことをしているなら、それぞれをサブ関数に分割する。

### 5-2. 関数の長さ（実践的目安）

| 行数 | 評価 |
|---|---|
| ~20行 | 理想的 |
| ~50行 | 許容範囲 |
| 100行以上 | 分割を検討する |

### 5-3. コードの流れを単方向にする（第11章）

```
// ❌ 関数内で「モード」によって動作が大きく変わる
function process(data, mode) {
  if (mode === "A") { ... }
  else { ... }  // 全く異なる処理
}

// ✅ モードごとに関数を分ける
function processAsA(data) { ... }
function processAsB(data) { ... }
```

## 6. コードの構造・組織化

### 6-1. 無関係な下位問題を抽出する（第11章）

関数の「主目的」を特定し、それ以外の処理（汎用的に使えるもの）を別関数に切り出す。

```
// ❌ URLパース処理が検索ロジックに埋め込まれている
function searchUser(url) {
  const parts = url.split("?");
  const params = new URLSearchParams(parts[1]);
  const userId = params.get("id");
  // ... ユーザー検索処理
}

// ✅ 下位問題を分離
function getQueryParam(url, key) { ... }

function searchUser(url) {
  const userId = getQueryParam(url, "id");
  // ... ユーザー検索処理
}
```

### 6-2. コードは段落に分ける（第12章）

空行でコードを「意味のかたまり」ごとに区切る。  
コメント（`// --- セクション名 ---`）でブロックの目的を示すとさらに明確になる。

### 6-3. 一貫性を保つ（第12章）

- プロジェクト内で統一した命名規則・コードスタイルを使う
- 類似の処理は同じパターンで書く（読者の「既視感」を活用する）
- 慣用句（イディオム）を使う: 言語・フレームワークの標準的な書き方に従う

---

## 7. テストコードへの適用

### 7-1. テストも同じ可読性原則に従う（第14章）

- テスト関数名は「何をテストするか」を明示する
  ```
  // ❌
  test("test1") { ... }
  
  // ✅
  test("残高が不足している場合、引き出しは失敗する") { ... }
  ```

- テストコードの冗長な「セットアップ」は関数に抽出する
- 入力 → 操作 → 検証 の3段階を明確に分ける（Arrange-Act-Assert パターン）

### 7-2. 最小限のテストを書く（第14章）

テストが複雑すぎる場合、それはプロダクションコードの設計問題のサインである可能性が高い。

## チェックリスト（レビュー前確認用）

### 命名
- [ ] 変数・関数名を見ただけで用途が分かるか
- [ ] 単位・状態・null 許容性が名前に含まれているか（必要な場合）
- [ ] `tmp`, `data`, `Manager` など意味のない汎称を使っていないか

### コメント
- [ ] コードを読めば分かることだけをコメントしていないか
- [ ] 「なぜ」を説明するコメントが必要な箇所に書かれているか
- [ ] TODO/FIXME/HACK はラベルと理由が明記されているか

### 制御フロー
- [ ] ネストが3段以上になっていないか
- [ ] 早期リターンで平坦化できるガード節があるか
- [ ] 条件式の左辺は「変化する値」になっているか

### 変数・式
- [ ] 複雑な式は説明変数または要約変数に分解されているか
- [ ] 同じ条件式を複数箇所に書いていないか
- [ ] 変数のスコープは必要最小限か

### 関数
- [ ] 1関数が複数の責務を持っていないか
- [ ] 汎用的な下位処理は別関数に分離されているか
- [ ] 引数の数は5個以下か（超える場合はオブジェクトに束ねる
